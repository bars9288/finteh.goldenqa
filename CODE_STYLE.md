# Именование Java-кода

Имена описывают роль объекта или действие и используют один словарь во всех модулях.

- Классы и интерфейсы — `UpperCamelCase`: `FullNameRule`, `ScenarioRepository`.
  Название правила уточняет, что оно проверяет: `PartyActualityDateRule`,
  `AttributeActualityDateRule`, `PhysicalPartyAttributeTypeRule`.
- Пакеты — строчными буквами, по предметной области: `greeting`, `web.mdm`.
- Методы — `lowerCamelCase`: действие либо название возвращаемых данных,
  например `validateBody`, `parseDateOrNull`, `commonRules`.
- Переменные — по содержимому и роли: `fieldsByName`, `forwardedHeaders`,
  `temporaryFile`. Короткие общепринятые имена `id`, `uri`, `i` допустимы,
  если контекст однозначен; случайные сокращения `f`, `attrs`, `typesErr` не используем.
- Логические значения читаются как утверждение: `hasMissingType`, `hasCompleteName`.
- Константы — `UPPER_SNAKE_CASE`: `ALLOWED_VALUES`, `BIRTH_DATE`, `LOGGER`.
- Суффиксы отражают роль: `Controller` для REST, `Endpoint` для Spring WS,
  `Mapper`, `Validator`, `Repository`, `Converter` — для соответствующих компонентов.
- Суффикс `DTO` сохраняется как соглашение проекта. Имена полей JSON/XML,
  SQL-колонок и ключей конфигурации меняются только как отдельное изменение контракта.
- Отложенные компоненты обозначаются префиксом `Legacy`; подсистемы таких
  компонентов находятся в `legacy.*`. Новые рабочие реализации размещаются отдельно.

При переименовании обновляются конструкторы, импорты, места использования,
тесты и ссылки в документации. После переноса Java-файлов выполняется
`mvn clean verify`, чтобы старые классы не оставались в артефактах сборки.
